# 열공라운지 「같이 공부하는 느낌」 아이디어 요청 (아스트라에게, 2026-11-11)

**이번에는 구현이 아니다.** 아이디어를 내고 평가해 달라. 코드는 건드리지 않는다. 작업 트리에 미커밋된 Live Activity 수정(`src/utils/liveActivity.js` 등)이 있으니 그대로 둔다.

## 사용자(개발자)의 고민

> 열공라운지가 지금도 충분히 좋지만, 사용자들이 조금 더 같이 공부하는 느낌을 갖도록 할 수 있는 아이디어가 있을까? 서로에게 부담을 주지 않으면서도, 같은 공간에서 공부하는 사람이 있다는 걸 느끼면서 힘이 될 수 있는 그런 것.

## 지금 라운지에 있는 것

설계 원본은 `docs/realtime-study-design.md`이고, 코드는 `src/screens/StudyRoomScreen.js`·`src/utils/studyRoom.js`·`src/utils/studyRoomCore.js`에 있다.

- **좌석 도면**: 카페·독서실·교실 3테마, 30석이다. 빈 책상을 누르면 자리를 옮긴다
- **공부 중 표시**: 과목 라벨과 경과 시간을 보인다. 화면을 끄고 공부하면 흐리게 하지 않고 달 표시로 올린다. 잠금 이탈은 자리 비움으로 보인다
- **오늘 누적**: 쉬는 사람 자리에는 오늘 누적 시간이 보인다. 좌석 아래 접이식 「오늘 이 방」 목록은 공부 중인 사람이 먼저, 그다음 누적 순이다
- **익명 응원**: 남의 자리를 누르면 엄지척을 보낼 수 있다. 받은 쪽 자리에 5분 동안 뱃지가 붙고, 방 밖에서도 토스트가 뜬다. **보낸 사람을 드러내지 않는 것이 설계 의도다**(아는 사이끼리만 주고받게 되는 것을 막는다)
- **방 밖 표시**: 집중 탭과 잠금 오버레이에 「우리 방 N명 집중 중」이 뜬다. 공부하는 동안에는 라운지 화면을 안 보기 때문에 넣은 것이다
- **안전장치**: 숨기기(로컬), 신고, 닉네임 필터
- **라운지 정원**: 호점마다 30명이다(STUDY2~5). 「다같이 집중」(공유 카운트다운)은 **코드 방 전용이고 라운지에는 없다.** 모르는 사람끼리라 불필요하다고 봤다

## 사용자층과 규모

- 수험생이 중심이고 미성년이 많다
- 라운지 명단은 10명 안팎이다. 하루에 실제로 공부하는 사람은 몇 명이고, **같은 시각에 겹치는 일은 드물다**
- 그래서 **지금 아무도 공부하고 있지 않을 때에도** 효과가 있는 아이디어가 특히 필요하다. 기존 설계 문서도 「방이 자주 비어 상호작용이 없다」를 핵심 결함으로 짚었다(11절)

## 바꿀 수 없는 제약

- **Firebase Spark(무료) 요금제**: 서버 함수가 없다. 서버에서 푸시를 보내거나 서버가 집계하는 일은 불가능하다. 동시 연결 상한은 100이다
- **RTDB 규칙**: 각자 자기 노드만 쓴다. 새 노드나 필드를 만들면 규칙을 고쳐 콘솔에 다시 게시해야 한다(`docs/firebase-database.rules.json`)
- **공유 데이터 최소화**(설계 0절): 닉네임·캐릭터·공부 중 여부(과목 라벨 포함)·오늘 누적만 올린다. 새로 올리는 데이터가 생기면 개인정보처리방침과 스토어 데이터 양식(Play 데이터 보안·App Store 개인정보)을 고쳐야 한다. 이것도 비용으로 계산해 달라
- **초당 네트워크 쓰기 금지**(배터리·요금)
- **하지 않기로 한 것**(설계 9절, 재론 금지): 친구·팔로우, 채팅·인증샷 등 자유 입력(모더레이션, 미성년), 주간·전체 랭킹, 서버 푸시
- **공부 앱이다**: 집중하는 동안 끼어드는 토스트·소리는 최소로 한다

## 「부담」을 재는 잣대

아이디어마다 아래 다섯 가지를 점검해 달라.
1. 답장이나 보답의 의무가 생기는가
2. 남과 비교하게 되는가(경쟁·순위)
3. 내가 원치 않게 드러나는가
4. 공부 흐름을 끊는가
5. 모르는 사람이 나를 골라 무언가를 하는 구조인가

## 답 — 같이 공부하는 느낌에 대한 독립 제안 (아스트라, 2026-11-11)

**지금은 동시 접속을 늘리는 기능보다, 서로 다른 시간에 공부해도 같은 공간을 쓰고 있다는 사실을 조용히 전하는 편이 맞다.** 다만 실제로 아무도 공부하지 않은 날까지 사람이 있었던 것처럼 꾸미면 안 된다. 그런 날에는 내 속도로 시작해도 괜찮다는 공간의 성격을 보여준다.

아래 1~4절을 먼저 작성·저장한 다음 오푸스 안을 읽고 5절에 비교를 붙인다. 독립안의 결론은 비교 후에도 원문으로 남긴다. 이번 작업은 문서뿐이며, 구현이나 데이터 수집을 승인하는 제안은 아니다.

### 1. 아이디어 7개와 평가

#### 먼저 확인한 현재 구현

- `status`는 사람별 **마지막 상태 한 건**이다. `todaySec`·`date`로 오늘 기록을 확인할 수 있지만, 날짜별 출석·과거 세션·실제 동시 공부 이력은 없다. `updatedAt`은 접속·하트비트·연결 해제에도 바뀌므로 공부 완료 시각이나 최근 공부일로 해석하면 안 된다.
- 당일 흔적을 낼 때는 **현재 방 명단과 상태를 교차 확인**하고, 나와 로컬 숨김 대상은 제외한다. 앱의 `getToday()`와 같은 날짜의 양수 `todaySec`를 근거로 쓴다. 지금 공부 중인 사람은 기존 `displayStatus`로 따로 표시한다. 아직 저장되지 않은 첫 세션을 오늘의 완료 기록에 억지로 넣지 않는다.
- 이것은 현재 멤버의 수신된 기록으로 만든 요약이다. 탈퇴·방 이동·기록 수정으로 달라질 수 있어, 그날 방을 거쳐 간 모든 사람의 확정 출석부가 아니다. 데이터 미수신·권한 오류·오프라인과 실제 0명도 구별해야 한다.
- 라운지의 익명 응원은 현재 코드에서 허용한다. 설계 11절에는 허용 설명과 미노출 설명이 함께 남아 있지만, 이번 판단은 요청서와 `StudyRoomScreen`의 실제 메뉴를 따른다.
- `오늘 이 방`은 공부 중 우선·누적 내림차순이며 행에 `1, 2, 3…`도 붙는다. 주간 랭킹은 없어도 비교를 유도하는 표현은 이미 있다.

작업량은 기존 구조를 아는 개발자 1명의 대략적인 인일이다. 로직 확인·iOS/Android 기기 확인·문서 작업을 포함한 범위이며, 스토어 처리 대기나 실제 효과 관찰 기간은 별도다. 아래 개인정보 비용은 이 요청서의 기준을 적용한 제품 판단이다.

#### A. 오늘 먼저 공부한 사람의 흔적

**무엇 / 느낌:** 라운지에 작은 요약 한 줄을 둔다. 다른 사람의 당일 기록이 확인되면 “오늘 이 방에는 먼저 공부한 사람이 있어요.” 지금 사람이 있다면 기존 집중 인원 표시를 우선한다. 시간·이름·정확한 인원·순서는 새 요약에 넣지 않는다. “지금 혼자여도 같은 날 이 공간을 쓴 사람이 있구나”가 목표다.

아무 흔적이 확인되지 않으면 “편한 시간에, 각자의 속도로 공부하는 공간이에요”처럼 사실을 꾸미지 않는 안내를 쓴다. “오늘의 첫 주인공”, “불을 이어 주세요”처럼 먼저 온 사람에게 역할을 맡기지 않는다. 추후 집중 탭의 시작 전·공부 종료 후에도 같은 한 줄을 재사용할 수 있다. 공부 중 잠금 화면에 새 알림을 띄우지는 않는다.

- **부담 다섯 가지:** 보답 없음 / 비교 낮음(수치·기여도 없음) / 노출 낮지만 0은 아님(소수 방에서는 다른 정보와 조합해 누구인지 추측 가능) / 방해 낮음(정적 문구) / 특정인 지목 없음.
- **데이터:** 기존 `members`, `status.date`, `todaySec`, 현재 상태 및 로컬 숨김 목록. 새 업로드 없음. 타인의 어제 기록을 내 기기에 누적 보관하지 않는다.
- **서버·규칙·정책:** 서버 함수·규칙 변경 없음. 라운지 안에서는 기존 구독 재사용. 방 밖 현재 구독은 상태 중심이므로 유효 명단과 숨김 목록을 연결하는 작업이 추가된다. 따라서 방 밖까지 포함해 “추가 읽기 0”이라고 약속하지 않는다. 수집 항목 추가는 없고 표현·공유 범위가 기존 고지와 맞는지 확인한다.
- **작업량:** 방 안 1~2일, 방 밖 재사용까지 총 2~4일 정도.
- **현재 규모의 효과:** **높음.** 다른 한 명이 오전에 공부하고 내가 저녁에 와도 성립한다. 당일 다른 사람의 기록이 정말 없으면 사회적 증거는 생기지 않는다. 자정에 사라지는 것이 단점이지만, 이를 감추려고 과거 이력을 새로 모으지는 않는다.

#### B. ‘오늘 이 방’을 순위 없는 동료 목록으로 바꾸기

**무엇 / 느낌:** 순번·시상대 아이콘·시간순 강조를 걷고, 좌석 순서처럼 안정된 순서로 사람을 보여준다. 공부 여부는 기존 상태 표시로 알아볼 수 있게 한다. 개인별 시간은 기본 요약에서 강조하지 않고 원할 때 펼쳐 본다. “얼마나 뒤처졌나”보다 “같은 공간의 사람들”을 먼저 보게 한다. 기존 좌석 이동과 정원은 유지한다.

- **부담 다섯 가지:** 보답 없음 / 비교 감소(시간을 펼치면 비교 가능성은 남음) / 노출 증가 없음 / 방해 낮음 / 특정인 지목을 새로 만들지 않음(기존 좌석 응원 메뉴는 별개).
- **데이터:** 기존 회원·좌석·상태·누적만 재사용. 새 업로드 없음. 숨긴 사람은 좌석 점유는 유지하되 새 목록·요약에서 활동 상세가 다시 드러나지 않게 한다.
- **서버·규칙·정책:** 서버·규칙 변경 없음. 노출을 줄이는 화면 변경이며 새 수집 항목 없음.
- **작업량:** 1~2일. 작은 글꼴·큰 글꼴과 숨김 상태의 표현 확인 포함.
- **현재 규모의 효과:** **중간 이상.** 동시 접속 없이도 성립하며, 하루 20분 공부한 사람이 몇 시간 공부한 사람 아래에 놓이는 부담을 줄인다. 새로운 상호작용을 만드는 힘은 약하지만 다른 아이디어의 부작용을 줄이는 바탕이다.

#### C. 다음에 올 사람에게 두는 ‘방 전체 응원’

**무엇 / 느낌:** 라운지를 직접 열었을 때만 선택할 수 있는 “이 방에 응원 남기기”를 둔다. 받는 사람을 고르지 않고, 자유 입력 없이 고정 문구 하나를 남긴다. 다른 사람은 나중에 방문해서 “같은 방 누군가가 응원을 남겼어요”를 조용한 카드로 본다. 이름·발신 시각·받은 수·읽음·답장 버튼은 없다. 보내기와 받기는 서로의 조건이 아니다.

남이 남긴 실제 응원이 있을 때만 표시한다. 최초안은 최근 24시간 이내 한 건 이상이면 카드 한 장으로 합치고, 내가 보낸 것과 숨긴 사람이 보낸 것은 제외한다. 받았다고 내 응원을 요구하지 않는다. 발신 UI는 하루 한 번으로 제한하되, 신뢰 가능한 서버 규칙 제한과는 구별한다.

- **부담 다섯 가지:** 보답 낮음(사회적 관습으로 남을 수 있어 답장·감사 유도 금지) / 비교 낮음(횟수·인기 표시 없음) / 노출 중간(발신 의사와 시각이 서버에 새로 남음) / 방해 낮음(라운지 방문 때만) / 특정인 지목 없음.
- **데이터:** 예를 들어 `roomEncouragement/{roomId}/{uid}`에 마지막 발신 `{at}` 한 건. 문구는 앱 상수로 둔다. 수신 확인은 로컬의 방별 기준값으로 처리하고 서버 읽음 기록은 만들지 않는다. 새 공유 데이터이므로 A·B보다 비용이 크다.
- **서버·규칙·정책:** 서버 함수 불필요. 방 멤버 읽기·본인 키만 쓰기·시각 상한·반복 갱신 제한·탈퇴 시 정리를 정의하고 RTDB 규칙을 콘솔에 게시해야 한다. **개인정보처리방침·Play 데이터 보안·App Store 개인정보 양식의 검토·갱신을 작업에 포함한다.** 기존 `cheers`의 대상 UID를 가짜 방 UID로 대체하는 편법은 쓰지 않는다.
- **보관 주의:** 24시간은 표시 유효기간이다. 함수 없는 환경에서 24시간 뒤 물리적 자동 삭제를 보장하지 않는다. 본인 최신 한 건 덮어쓰기·본인 탈퇴 삭제·허용된 오래된 값 정리 정책을 따로 정하고 실제 잔존 범위를 고지한다. UI 익명과 데이터의 비식별성도 다르다. UID로 작성자와 연결될 수 있다.
- **작업량:** 4~7일. 규칙·반복 입력·숨김·방 이동·정리·로컬 중복 노출 확인 및 고지 작업 포함.
- **현재 규모의 효과:** **잠재적으로 높음.** 보내고 받는 시각이 달라도 된다. 다만 몇 명의 자발적 발신이 있어야 하며 운영자가 대신 남기거나 시스템 문구를 실제 사용자 응원으로 위장하면 안 된다. A·B를 확인한 뒤의 2차 후보로 둔다.

#### D. 기존 개인 응원을 다음 방문까지 조용히 보관하기

**무엇 / 느낌:** 지금의 5분 좌석 배지는 유지하고, 최근 24시간 내에 받은 응원은 다음 비집중 화면 방문에서 한 번 볼 수 있게 한다. 새 토스트 대신 작은 수신 카드로 보여준다. 공부 중 들어왔다면 종료 후나 다음 방문까지 기다린다. “내가 없을 때도 누군가 응원했구나”를 느끼게 한다.

- **부담 다섯 가지:** 보답 중간(누군가 나에게 했다는 사실이 남음) / 비교 중간(인기 수를 숨겨도 받는 사람·못 받는 사람 차이) / 노출 중간(특정인에 대한 발신 관계는 이미 존재) / 방해 낮음(중간 토스트를 줄일 때) / **특정인 지목 있음**(기존 구조 그대로).
- **데이터:** 기존 `cheers/{roomId}/{targetUid}/{senderUid}.at`와 로컬 수신 기준값. 새 서버 필드 없이 가능하다. 같은 발신자의 재전송은 이전 값을 덮으므로 응원의 완전한 이력이나 정확한 총건수를 복원할 수 없다. 첫 스냅샷을 현재처럼 전부 무시하면 오프라인 수신을 놓치므로 별도 설계가 필요하다.
- **서버·규칙·정책:** 기본안은 서버·규칙 변경 없음. 수신 기준값은 UID·방 변경/탈퇴 때 정리하고 숨김 발신자를 걸러야 한다. 새 수집 항목은 없지만 보이는 기간과 전달 방식이 달라지는 만큼 기존 설명·정책 점검 비용을 잡는다. 기간 제한을 서버 삭제 보장으로 쓰지 않는다.
- **작업량:** 2~4일. 재설치·재진입·여러 응원·방 이동·집중 중 수신의 중복/누락 확인 포함.
- **현재 규모의 효과:** **중간.** 동시 접속 부족은 완화한다. 그러나 특정 자리를 선택해야 하므로 혼자 자주 쓰는 사람이 계속 아무 응원도 못 받을 수 있다. C와 동시에 넣기보다, 새 공유 데이터 비용을 감당하기 어려울 때의 대안으로 비교한다.

#### E. 혼자 와도 익숙한 ‘내 자리 다시 펼치기’

**무엇 / 느낌:** 라운지에 돌아오면 기존 내 좌석을 쉽게 찾게 하고, 내 기기에서만 작은 책갈피나 안내를 보여준다. “내 자리는 여기예요. 편한 속도로 시작해요.” 같은 간단한 표현이다. 앱 안의 공부 시작과 종료를 좌석의 조용한 상태 변화로 연결하되 별도 출석·퇴실 버튼은 만들지 않는다. “다시 와도 익숙한 공부 장소”가 목표다.

- **부담 다섯 가지:** 보답 없음 / 비교 없음 / 추가 노출 없음(내 기기에서만) / 방해 낮음(입장 때만, 움직임 최소) / 특정인 지목 없음.
- **데이터:** 기존 내 좌석과 내 타이머·로컬 세션. 필요하면 로컬 표시 여부 한 건만 저장한다. 타인의 방문 이력을 보관하거나 내 출석을 새로 서버에 올리지 않는다.
- **서버·규칙·정책:** 서버·규칙 변경 없음. 기존 좌석이 다른 사람이 보기에도 영구 예약된다는 약속을 하지 않는다. 유령 정리·좌석 충돌·방 이동을 따른다. 새 수집 항목 없음.
- **작업량:** 1~2일. 새 캐릭터 애니메이션 제작은 이 추정에서 제외한다.
- **현재 규모의 효과:** **공간 친숙함에는 중간, 타인과의 연결에는 낮음.** 다른 사람이 당일 한 명도 없어도 작동한다. 하지만 이것만으로 함께 공부하는 느낌이 생겼다고 평가하면 안 된다. 연속 출석·며칠째·놓친 날 강조를 붙이면 원래 장점이 사라진다.

#### F. 방 전체 공부시간으로 함께 만드는 책 한 권

**무엇 / 느낌:** 개인 순위 대신 오늘 방 전체의 누적 시간이 책 그림의 페이지나 책등을 채우게 한다. “각자의 공부가 함께 쌓인다”는 감각을 노린다. 개인 기여도·목표 달성 알림·보상은 없는 가장 약한 형태부터 평가한다.

- **부담 다섯 가지:** 보답/기여 의무 중간 / 비교 중간(남의 방·어제 수치로 확장하기 쉬움) / 노출 중간(한두 명이면 합계가 개인 시간과 비슷함) / 방해 낮음(정적 표시일 때) / 특정인 지목은 없지만 소수 방에서 기여자 추측 가능.
- **데이터:** 같은 날짜의 기존 `todaySec`를 명단과 교차해 클라이언트에서 합산. 새 업로드 없이 가능하다. 진행 중 경과 시간을 단순히 더하면 이미 기록한 세션과 겹칠 수 있어 합산하지 않는다.
- **서버·규칙·정책:** 당일 표시만 하면 서버·규칙 변경 없음. 과거 책장을 남기거나 누적 달성 보상을 만들면 새 공유 이력이 필요하므로 별개 범위와 정책 비용이 생긴다.
- **작업량:** 당일 표시만 2~3일. 과거 보존은 별도 산정.
- **현재 규모의 효과:** **낮음~중간, 지금은 보류.** 한 사람의 긴 공부가 방의 성과가 되고, 짧게 공부한 사람은 기여 압박을 느낄 수 있다. 기록 수정·탈퇴·자정 때문에 책이 줄어드는 문제도 있다. 숫자 대신 그림을 써도 경쟁·의무가 저절로 없어지지는 않는다. A보다 추가 이득이 작다.

#### G. 느슨한 공부 시간대 겹침 찾기

**무엇 / 느낌:** 선택한 사람만 “주로 오전 / 오후 / 저녁” 정도의 넓은 시간대를 남기고, 개인 명단 없이 방의 시간대 경향을 본다. 예약·약속·호출은 없다. “내가 오는 시간에도 누군가 있을 수 있구나”를 노린다. 실제 접속 예측이라고 표현하지 않는다.

- **부담 다섯 가지:** 약속/응답 의무 중간 / 비교 낮음 / **노출 높음**(미성년자의 생활 패턴) / 방해 낮음(알림 없을 때) / UI 지목은 없어도 작은 방에서는 누구의 시간대인지 추측 가능.
- **데이터:** 본인이 선택한 시간대라는 새 공유 필드. 기존 `updatedAt` 하나로 평소 시간대를 추론해서는 안 된다. 과거 접속 기록을 몰래 모으는 방식도 제외한다.
- **서버·규칙·정책:** 서버 함수 없이 본인 노드만 갱신할 수 있지만 규칙·철회/삭제·고지와 스토어 양식 갱신이 필요하다. 한두 사람의 응답만 있는 구간을 숨기는 방법도 익명성을 보장하지 않는다.
- **작업량:** 4~6일. 정책·낮은 표본의 표시 조건 포함.
- **현재 규모의 효과:** **낮음, 지금은 하지 않는다.** 겹치지 않아도 힘이 되는 경험이 아니라 결국 동시 접속을 기다리게 한다. 표본이 적어 실용성은 약하고 정보 노출 비용이 크다.

### 2. 우선순위 상위 셋

1. **A — 오늘 먼저 공부한 사람의 흔적.** 지금의 핵심 문제인 시간 불일치에 직접 대응한다. 누가 몇 시간 했는지 더 드러내지 않고 기존 데이터만으로 작은 실험을 할 수 있다. 먼저 방 안에서 검증하고, 유효 명단과 숨김 처리를 갖춘 뒤 방 밖으로 연결한다.
2. **B — 순위 없는 동료 목록.** 함께 있다는 표현을 추가하면서 아래에서는 줄 세우면 메시지가 충돌한다. 규모가 작아도 바로 적용 가치가 있고 데이터·규칙 비용이 낮다. 경쟁을 좋아하는 일부 사용자의 반응도 확인하되, 이 라운지의 목적은 요청서의 ‘부담 없는 동행’으로 정한다.
3. **C — 방 전체 응원.** 가장 직접적인 비동시 상호작용이며 특정인을 선택하지 않는 장점이 있다. 다만 새 데이터·규칙·정책 비용 때문에 **첫 배포 범위에는 넣지 않는다.** A·B 이후에도 사용자들이 실제 사람의 의사 표현을 원한다고 확인될 때 검토한다.

첫 실험은 A 하나로 시작하고, B를 다음 관찰 단계에서 적용하는 편이 효과를 구분하기 쉽다. 묶어 적용한다면 결과도 ‘A+B 묶음의 반응’으로만 기록한다. E는 빈 날의 기본 경험을 다듬는 보조안이고, D는 C의 비용을 피하는 대신 개인 지목 부담을 감수하는 대안이다. 일곱 개를 모두 기능으로 만들 이유는 없다.

### 3. 위험과 하지 말아야 할 것

- **사람이 없을 때의 정직함:** 봇·가짜 이용자·가짜 응원·어제 활동을 오늘로 표시하기·지금 없는 사람을 집중 중으로 그리기는 하지 않는다. 시스템의 일반 격려와 다른 사람이 실제 남긴 응원을 구별한다. 데이터가 안 왔다는 이유로 “오늘 아무도 안 왔어요”라고 쓰지도 않는다.
- **소수 인원의 재식별:** ‘익명’ 문구만 붙인다고 익명이 되지 않는다. 정확한 시각·과목·기여량·참여 순서를 합치면 소수 방에서 특정인이 드러난다. 새 요약에는 이 조합을 만들지 않는다. 숨긴 사람의 활동을 요약이나 새 수신 카드로 다시 드러내지 않는다.
- **부담을 옮기지 않기:** 방 목표·연속 불꽃·깨지는 식물·‘네가 와야 유지돼요’·응원 답례·미접속 죄책감은 제외한다. 방 전체 합계도 압박이 될 수 있다. 응원 받기 위해 공부량이나 접속 횟수를 채우게 하지 않는다.
- **집중 보존:** 공부 중 새 토스트·소리·진동·카운트 상승 애니메이션을 추가하지 않는다. 확인하려고 라운지를 계속 열게 만드는 새 메시지 숫자도 피한다. 공부를 끝낸 뒤 사용자가 보는 화면이 우선이다.
- **권한·잔존 데이터:** 다른 사람 노드에 대리 기록하지 않는다. 수신자는 자기 로컬 표시만 처리하고 공유 집계값을 서로 덮어쓰지 않는다. 표시 만료와 물리 삭제는 구별한다. 클라이언트 자기신고 값에는 보상이나 정확한 경쟁 지표를 걸지 않는다.
- **규모를 감추려고 범위를 넓히지 않기:** 모든 라운지의 상태를 추가 구독하거나 서로 다른 방을 몰래 합쳐 큰 숫자를 만들지 않는다. 한 방의 기존 구독을 우선하며 초당 쓰기·서버 집계·서버 푸시는 제안하지 않는다. 친구·팔로우·자유 입력·인증샷·주간/전체 랭킹도 재론하지 않는다.
- **기존 동작 보호:** 방 이동·탈퇴·자정·연결 실패·숨김에서 요약을 다시 판정해야 한다. 라운지 표시 때문에 타이머 시작/종료나 로컬 세션 원본을 바꾸지 않는다. 이번 아이디어 검토에서는 미커밋 Live Activity 작업을 건드리지 않는다.

### 4. 효과를 재는 방법과 한계

**현재 숫자로 확인할 수 있는 것은 이용 규모와 최근 활동 신호의 변화다. ‘함께한다고 느꼈는가’는 직접 측정할 수 없다.** 이번에는 Firebase를 실제 조회하거나 측정 코드를 변경하지 않았다. 읽기 전용 집계를 쓰는 관찰 계획이다.

`scripts/rtdb-usage-count.mjs`는 `max(joinedAt, updatedAt)`을 최근 활동으로 센다. 새 가입과 접속/연결 상태 갱신도 포함되므로 `active.d1/d3/d7`을 ‘공부한 인원’·‘재방문율’·‘D7 유지율’이라고 부르면 안 된다. 현재 명단만 세므로 탈퇴한 사람도 빠진다. 익명 계정 재설치는 한 사람의 연속 관찰이 아니다.

| 볼 것 | 현재 가능한 기록 | 판단할 때의 제한 |
|---|---|---|
| 라운지 규모 | STUDY2~5의 명단 수, 호점별 분산 | 자리를 차지한 인원이며 현재 공부 중 인원은 아님. 유령 정리·방 이동으로도 변함 |
| 최근 활동 신호 | 라운지의 최근 1·3·7일 인원, 가능하면 14일도 보조 | 사람별 마지막 신호의 시점만 반영. 매일 값의 합을 방문 횟수로 세지 않음 |
| 명단 대비 최근 활동 | 7일 신호 인원 / 같은 시점 라운지 명단 수를 원수치와 함께 기록 | 명단 정리만으로 비율이 오를 수 있음. 분모 0 처리, 작은 표본에서 비율만 강조하지 않음 |
| 운영 변화 | 동일 날짜의 배포·모집·시험 일정·기능 장애·유령 정리 사실 | 기존 집계의 새 가입 지표에는 코드 방도 섞여 있으므로 라운지 신규 수로 단정하지 않음 |

**관찰 순서:** 변경 전 7일, 변경 후 14일 정도를 같은 KST 시각·같은 읽기 범위로 본다. 하루 한 번의 작은 집계로 시작하고 uid·닉네임·원본 상태·행동 타임라인은 보고서에 남기지 않는다. 이미 있는 집계는 재사용하되, 새 화면 아이디어를 위해 실시간 운영 DB 감시를 추가하지 않는다. 관찰 기간의 길이는 효능 보장이 아니라 운영 부담을 낮춘 시작점이다.

명단 약 10명에서는 1~2명의 변화가 전체 비율을 크게 바꾼다. 신규 모집·시험 기간·다른 출시 변경을 함께 적고, 증가가 있어도 이 기능의 인과 효과라고 결론 내리지 않는다. 기존 CLI로는 기능 노출 여부, 라운지 열람 횟수, 응원 읽음, 실제 동시 공부 시간, 공부 중 앱 확인 증가를 알 수 없다. 이를 알아내겠다고 이번 범위에서 새 분석 이벤트를 수집하지 않는다.

**느낌 검증은 별도다.** 기존에 피드백을 주는 사용자와 기기 확인을 하게 된다면, 실제 문구와 화면을 보여주고 “언제 같이 있다고 느꼈는지”, “누가 나를 보고 있거나 답해야 할 것 같았는지”, “공부 중 다시 확인하고 싶어졌는지”를 묻는다. 새 연락이나 설문 전송은 이번 작업에 포함하지 않는다. 그런 피드백 통로가 없으면 현재 숫자만으로 정서적 효과를 확인할 수 없다고 남긴다.

유지할 근거는 작은 활동 신호 변화와 구체적인 긍정 경험이 함께 있을 때다. 거짓 존재감·감시 느낌·답례 부담·불필요한 확인 행동이 보고되면 활동 수가 늘어도 표현을 줄이거나 되돌린다. 숫자가 유지된다는 이유만으로 실패라고 단정하지도 않는다. 공부 앱에서 라운지 체류시간 증가는 목표로 삼지 않는다.

### 5. 오푸스 안을 읽은 뒤의 비교와 비평

1~4절을 요청서 아래에 실제 저장한 뒤 처음으로 [`lounge-together-opus-ideas.md`](lounge-together-opus-ideas.md)를 열었다. 아래는 그 이후의 비교이며 독립안은 고쳐 맞추지 않았다. 근거는 현재 저장소 코드·규칙·읽기 전용 집계 스크립트이고, 사용자 효과를 실험한 결과는 아니다.

#### 겹치는 판단과 오푸스 안에서 더 좋은 점

**접속이 겹치지 않는 시간을 다뤄야 한다는 진단, 시작 전·종료 후에 보여주자는 방향, 고르거나 답하지 않아도 되게 하자는 원칙은 같다.** 내 A·F는 오푸스 2번과, 내 C는 오푸스 5번과 겹친다.

오푸스 1번은 특히 **공부를 끝낸 바로 그 순간에 그 세션의 경험을 되돌려준다**는 점이 좋다. 방 안에 정보를 더 놓는 방식보다 전달 시점이 구체적이다. 내 A의 방 밖 확장에도 이 장점을 반영할 가치가 있다. 다만 아래 이유로 실제 함께한 시간이나 고유 인원 수를 계산하는 원안까지 채택하지는 않는다.

오푸스 2번의 책상 표현은 추상적인 요약 한 줄보다 공간의 느낌을 잘 전달할 수 있다. 표현력에서는 장점이 있다. 반면 누구의 흔적인지 드러나는 좌석별 불빛 대신 **방 전체의 정적인 책갈피 같은 표시**로 바꾸면 내 A의 낮은 노출 수준과 결합할 수 있다. 이 표시는 실제 당일 기록이 있을 때만 쓰고, 현재 공부 중 표시와 모양도 구별한다.

#### 안별 판단

| 오푸스 안 | 평가 | 지금 채택할 범위 |
|---|---|---|
| 1. 함께한 시간 | 종료 시점의 전달은 좋다. 정확한 시간·인원 집계와 ‘작은 작업’이라는 평가는 수정 필요 | 종료 화면의 조용한 동행 메시지만 후보. 시간·고유 인원·주간 함께한 시간은 보류 |
| 2. 공동 누적과 온기 | 지금 규모에 가장 맞는 문제를 다룬다. 공동 숫자도 압박·추측을 만들 수 있음 | 개인별 흔적·정확한 합계보다 방 전체에 당일 흔적이 있다는 A 방식 우선 |
| 3. 정각 집중 | 사람의 초대를 없앤 점은 좋지만 시간 약속의 부담과 참여 판정 문제가 남음 | 첫 실험에서 제외. 지금 없는 동시성을 기다리게 하는 방향보다 비동시 경험 우선 |
| 4. 신규 표시·환영 | 따뜻한 첫인상이라는 목적은 좋다. 현재 규모에서 효과보다 지목·오인 비용이 큼 | 공개 신규 배지 대신 당사자만 보는 사용 안내. 타인에게 신규 사용자 지목은 하지 않음 |
| 5. 모두 화이팅 | 개인 선택 없는 응원이라는 핵심에 동의 | 다음 방문까지 남기는 내 C 방식이 현재 규모에 더 맞음. 규칙·정책 비용은 정식으로 산정 |
| 6. 어제 이 시간 N명 | 과거에도 쓰는 공간이라는 감각은 좋으나 관측 공백과 이력 보관 비용이 큼 | 보류. 부분 관측을 과거 실제 인원으로 표시하지 않음 |

#### 빠진 위험과 바로잡을 전제

**1번: `roomStudyingCount`는 그 시점의 상태 표시용 인원이지 세션 이력이 아니다.** `useAppState`는 지금 상태를 주기적으로 다시 계산할 뿐이고, 화면을 끄거나 앱이 중단된 동안 모든 변화를 관측한다는 보장이 없다. `displayStatus`는 마지막 갱신부터 60분 또는 예정 종료+5분까지 상태를 신뢰하는 규칙도 쓴다. 그래서 실제 공부 시간이 겹쳤는지와 표시상 겹쳤는지가 다를 수 있다.

카운트만 보고 “3명과 함께했어요”의 서로 다른 3명도 알 수 없다. A가 나가고 B가 들어와 계속 1명이어도 같은 수치이고, 최댓값 3 역시 세션 전체의 고유 인원 수가 아니다. UID별 구간을 더 추적하면 로컬 이력·구독 수명·앱 복귀·휴식 페이즈 처리가 늘어나며, 그래도 관측하지 못한 시간을 복원할 수는 없다. **서버 변경이 없다는 것과 구현·검증 비용이 작다는 것은 별개다.**

가볍게 살리려면 실제 세션의 유효한 관측이 있을 때만 “공부하는 동안 같은 방의 다른 공부 표시를 확인했어요” 정도의 비수치 메시지를 검토할 수 있다. 이 문구도 사용자에게 자연스러운지 확인해야 한다. 관측이 없던 세션에는 A의 당일 흔적을 별도로 쓸 수 있지만, 이를 그 세션에서 함께 있었다는 뜻으로 바꾸지 않는다.

**2번: ‘다녀간 9명’은 현재 데이터가 보장하지 않는다.** 현재 방 명단과 최신 당일 기록은 오늘 탈퇴하거나 이동한 사람까지 포괄하는 방문 이력이 아니다. `updatedAt`은 방문·공부 완료를 뜻하지 않는다. 합계를 쓰더라도 “현재 멤버의 오늘 기록 합계”라는 범위에 가깝고, 진행 중 시간이 다 포함되는 것도 아니다.

또 ‘모두의 숫자’라고 비교가 사라지는 것은 아니다. 실제로 공부하는 사람이 몇 명이면 합계에서 개인 기여를 추측하기 쉽다. 온기가 붙은 개인 좌석은 누가 오늘 공부했는지 더 눈에 띄게 한다. 오래 남은 불빛이 지금도 공부 중이라는 오해를 낳을 수도 있다. **이미 있는 목록 수준의 부담이면 충분하다는 기준보다, B처럼 기존 비교 부담도 줄이는 편**이 요청 취지에 맞는다.

**3번: 시작하는 사람이 없어도 참여 압박은 남는다.** 정각을 놓쳤다는 느낌, 50분을 못 채우면 중간에 빠지는 느낌이 생길 수 있다. 또 `startedAt`은 현재 타이머의 시작 시각이지 정각 세션 참여 동의가 아니다. 정각 근처에 자기 공부를 시작했다고 자동 참가자로 세면 의미가 달라진다. 시작 시각 한 개만으로 그 라운드의 전체 참가자도 복원할 수 없다.

벽시계로 도는 공용 리듬 자체는 새 서버 없이 가능하지만, 참가자 수·완주·함께 시작했다는 표시는 따로 증명해야 한다. 선택형 로컬 알림도 방해가 없다는 뜻은 아니다. 기존 읽기 전용 최근 활동 수에는 정각 참가 여부가 없으므로 “효과를 재기 좋다”는 설명도 현재 측정 수단으로는 뒷받침되지 않는다. 라운지의 공유 카운트다운 제외 결정을 지금의 첫 실험에서 뒤집을 근거는 부족하다.

**4번: `joinedAt`은 첫 가입 시각이 아니라 이 방의 가입 시각이다.** 방 이동·탈퇴 후 재가입·유령 정리 뒤 자동 복귀도 새 멤버 기록을 만든다. 그래서 ‘앱에 처음 온 사람’을 뜻하지 않는다. 배지가 작아도 모르는 사람이 특정 신규 사용자를 골라 반응하는 구조는 그대로다. 익명 응원이어서 답장 의무가 낮다는 것과 원치 않는 주목이 없다는 것은 다르다. “처음 며칠이 가장 많이 떠난다”는 주장도 이 앱의 현재 집계에서 확인된 사실은 아니므로 가설로 두어야 한다.

**5번: 비동시 전달로 바꾸면 우선순위가 달라진다.** 오푸스 안은 지금 아무도 없으면 수신자가 없다는 이유로 뒤로 뒀다. 내 C는 실제 남겨진 응원을 다음 방문 때 읽게 해 이 조건을 없앤다. 이 차이는 단순한 연출보다 현재 규모에 중요하다. 다만 새 노드가 생기므로 “응원과 비슷하니 양식 변경도 작다”를 전제로 작업량을 줄이지 않는다. 요청서가 요구한 세 고지·양식의 검토·갱신을 포함한다.

보낸 사람별 키는 **저장 건수와 중복 개수**를 제한할 뿐, 갱신 횟수를 막지는 않는다. 동일 키의 `at`을 계속 바꿀 수 있으므로 한 시간 한 번이라는 제한을 보장하려면 규칙에서도 따로 검증해야 한다. 기존 `cheers` 규칙에는 그 간격 검증이 없다. 토스트를 끄더라도 반복 갱신에 따른 노출·쓰기 문제를 확인해야 한다. 새 C의 하루 한 번도 같은 기준이다.

**6번: 내 폰이 못 본 시간은 모른다.** 폰에 일부 인원 관측을 쌓아도 “어제 이 시간에 N명이 있었다”는 완전한 이력이 되지 않는다. 보관하는 대상이 개인 UID 없이 합계뿐이어도 새 관찰 이력이고, 자주 켜 보는 사람만 더 풍부한 기록을 갖게 된다. 라운지 확인 빈도를 늘릴 유인을 만들 가치가 있는지 먼저 따져야 한다.

**효과 측정:** 오푸스의 “한 번 온 사람이 다음 주에 다시 오는지”는 현재 집계로 직접 알 수 없다. 지난주에 한 번 갱신하고 다시 오지 않은 사람과 여러 번 돌아온 사람 모두 마지막 시각 한 건으로 남는다. 주차별 익명 사용자 집합을 별도로 저장해 교집합을 구하면 반복 활동 신호의 대리지표는 만들 수 있겠지만, 그 자체가 현재 집계보다 넓은 추적이며 라운지 화면 재방문도 아니다. 이번에는 제안하지 않는다. 11월 초 수치가 있어도 명단 정리·모집·출시 변화와 같은 기준인지 확인한 뒤 참고값으로만 쓴다.

#### 비교 후 권하는 결정

**A의 당일 흔적을 우선하고, B로 비교 부담을 줄인다는 독립안의 우선순위를 유지한다.** 오푸스에서 가져올 것은 종료 후의 전달 시점과 공간을 느끼게 하는 작은 표현이다. 정확한 공동 시간·참가자 수·정각 모임·신규 지목을 함께 묶어 넣지는 않는다.

다음 단계의 실제 상호작용은 C처럼 **대상을 고르지 않고, 다음에 와도 받을 수 있고, 답례를 요구하지 않는 응원**이 가장 유망하다. 먼저 작은 화면 변화로 반응을 보고 새 데이터의 비용을 감수할 이유가 생겼을 때 별도로 설계한다. D는 그 비용을 줄이는 대안이지만 개인 지목이라는 차이를 숨기지 않는다.

이번 답은 아이디어·평가 문서이며 구현 완료나 효과 입증을 뜻하지 않는다. 앱 코드·RTDB 규칙·Live Activity 미커밋 작업은 수정하지 않았고, 운영 DB 조회·외부 메시지·푸시·배포도 수행하지 않았다.
