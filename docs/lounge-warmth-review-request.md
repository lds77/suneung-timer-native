# 검토 요청 — 라운지 온기·책 더미·명단 (아스트라에게, 2026-11-11)

**검토만 해 달라. 코드·규칙·문서는 고치지 않는다.** 지금 이 작업 트리로 미리보기 APK를 빌드하고 있다. 빌드 도중에 소스가 바뀌면 산출물이 어느 시점 코드인지 알 수 없게 된다. 미커밋 Live Activity 수정(`src/utils/liveActivity.js` 등)도 그대로 둔다. 답은 이 문서 아래에 붙이고, 커밋은 이 문서만 한다.

## 무엇이 바뀌었나

커밋은 `6a52de9`(코드)와 `70a9c2c`(규칙)다. 기획 배경은 `docs/lounge-together-astra-request.md`(네 답 포함)와 `docs/lounge-together-opus-ideas.md` 끝의 「종합」에 있다. 사용자가 고른 안은 셋이다.

1. **온기:** 공부를 멈춘 뒤 30분 동안 그 자리를 옅은 주황으로 보이고, 점점 옅어진다. 끝난 시각을 알려고 status에 `endedAt`을 더했다
   - `useAppState.sendStudyPresence`: 「공부 중 → 멈춤(종료·일시정지)」 순간에 `Date.now()`를 잡는다. 앱을 다시 켜서 그 순간을 못 봤으면 오늘 마지막 세션의 `endedAt`으로 대신한다
   - `studyRoomCore.buildPresence`: 멈췄을 때만 `endedAt`을 싣는다. 공부 중에는 `null`(RTDB update에서 삭제)이다. `presenceSig`에도 넣었다
   - `displayStatus`의 `warm`: 공부 중이 아니고, 시작 시각이 없고, `endedAt`이 있을 때 30분 페이드다. 공부를 끝내고 앱을 닫으면 onDisconnect가 state를 `bg`로 바꾸므로 state로 판정하지 않는다. 끝이 정해진 타이머가 백그라운드에서 끝나 알리지 못한 경우에는 `plannedEndAt`을 끝난 시각으로 본다
   - `studyRoom.syncPresence`: 전송이 실패하면 `endedAt`만 빼고 한 번 더 보낸다. 규칙이 되돌려져도 「공부 중」 표시는 살리려는 안전장치다
2. **책 더미:** 오늘 공부량을 숫자 대신 책 1~3권으로 보인다(1시간 미만 / 1~3시간 / 3시간 이상, `todayStack`). 좌석과 「오늘 이 방」 모두 그렇고, 나도 남과 똑같이 보인다. 정확한 기록은 통계에 있다는 안내 한 줄을 뒀다
3. **오늘 이 방:** 시상대·순번·공부시간 내림차순을 걷었다. 순서는 공부 중 → 방금 전까지 → 나머지, 각 묶음 안에서는 자리 번호 순이다(`sortMembers`)

**규칙은 이미 운영에 게시했다.** 운영 규칙을 먼저 읽어 보니 저장소 파일과 한 군데가 달랐다. 응원 `nick` 칸이 운영에만 있었고, cheers에는 `$other` 거부가 걸려 있다. 그래서 저장소를 운영 + `endedAt` 한 칸과 같게 맞춘 뒤 게시했고, 게시 후 운영과 저장소가 같은 것을 확인했다.

## 내가 확신 못 하는 자리 — 여기를 중점적으로

1. **끝난 시각을 잡는 방식**(`presenceWasRunningRef`·`presenceEndedAtRef`). 다음 상황에서 틀린 온기가 생기거나 빠지는지 봐 달라
   - 타이머 둘 사이 전환, 랩 타이머, 뽀모 휴식 페이즈, 일시정지 후 재개
   - 앱 재시작 직후 타이머 복원, 스냅샷 캐치업으로 세션이 늦게 기록되는 경우
   - 방 이동·재입장
   - 같은 effect가 여러 번 불리는 경우
2. **`syncPresence` 재전송과 `lastPresenceSig`**: 재전송이 성공하면 sig는 endedAt을 포함한 값으로 남는다. 그 뒤 같은 상태에서 전송이 영영 막히는 경로가 있는가. 네트워크 실패와 권한 거부를 구별하지 않는데, 그 탓에 생기는 문제가 있는가
3. **`displayStatus` 온기 조건**의 거짓 양성과 거짓 음성. 특히 옛 버전 앱(endedAt을 안 씀)과 새 버전이 섞인 방, `headlessHeartbeat`(state studying만 쓴다), onDisconnect의 `bg`
4. **OTA 호환**: 나갈 곳은 runtime 1.0.43(양 플랫폼) 한 번이다. 이번 변경이 1.0.43 네이티브 바이너리에 없는 것을 쓰는 데가 있는가
5. **개인정보 고지**: 처리방침 2항은 공유 정보를 「현재 공부 중 여부와 타이머 이름(과목명), 공부 모드, 시작·예정 종료 시각 / 오늘 공부시간 합계」로 적는다. 「마지막으로 멈춘 시각」을 더해야 한다고 본다(문구는 내가 고친다). Play 데이터 보안·App Store 개인정보 양식에서 바꿀 범주가 있는가
6. 화면: 숨긴 사용자(좌석·명단에서 온기·책이 새는가), 내 자리, 큰 글꼴, 다크 모드에서 주황 온기와 책 색의 대비

## 답의 형식

찾은 것을 **P1(사용자 데이터·표시가 틀린다, 출시를 막는다) / P2(고쳐야 한다) / P3(작은 것)**으로 나눠 달라. 하나마다 재현 조건, 근거 코드 위치, 고칠 방향을 적는다. 없으면 「없음」이라고 적는다.

## 답 — 온기·책 더미·명단 검토 (아스트라, 2026-11-11)

**P1 1건, P2 5건, P3 1건. 현재 상태로 출시/OTA 승인은 보류한다.** 가장 중요한 것은 지연된 축소 재전송이 새 공부 상태를 덮는 문제다. 온기의 시각을 만드는 경로와 전송하는 경로도 아직 일관되지 않다. 사용자 선택인 온기·책 더미·순위 없는 명단 자체를 다시 기획하자는 의견은 아니다.

검토 시작 기준은 `sdk56`의 `5a53aa4`, 구현 `6a52de9`, 규칙 `70a9c2c`다. 검토 중 별도로 추가된 책 그림 커밋 **`ae3c296`도 읽고 반영했다.** 온기·전송·규칙 파일은 그대로였으며, 아래 화면 코드 위치와 책 평가는 `ae3c296` 기준이다. 관련 기존 테스트 **2 suites / 85 tests 통과**. 별도로 실제 함수 본문과 순수 모듈을 읽어 네트워크 대역으로 재현했다. 운영 Firebase·규칙 에뮬레이터·실기기에서 재현한 것은 아니므로 장애 빈도나 APK의 시각적 완성도까지 입증하지 않는다.

앱 소스·규칙·설정·다른 문서는 수정하지 않았다. 미커밋 Live Activity 작업도 보존했다. 진행 중인 APK 빌드에 명령을 보내거나 재빌드하지 않았다. 이 답만 요청서 아래에 추가한다.

### P1 — 출시를 막는 문제

#### W-01. 이전 idle의 재전송이 재개된 공부를 덮고, 복구 전송까지 중복으로 판단한다

- **재현 조건:** `endedAt`을 포함한 종료/일시정지 전송 A가 지연됐다가 거부되는 동안 사용자가 다시 공부를 시작해 전송 B가 나간다. A의 실패 처리에서 `endedAt`만 뺀 A′가 B 뒤에 쓰인다. 예를 들어 `endedAt` 미지원 규칙으로 되돌린 환경에서는 A만 거부되고, `endedAt: null`인 B와 필드가 없는 A′는 통과할 수 있다. 삭제 값의 `.validate` 처리 차이는 [Firebase 규칙 문서](https://firebase.google.com/docs/database/security/rules-conditions#validating_data)에도 명시돼 있다.
- **근거:** `src/utils/studyRoom.js:515`의 `syncPresence`, 특히 시그니처를 먼저 저장하는 `:522`와 무조건 이전 payload를 재사용하는 `:529`~`:534`. 재시도 직전에 최신 요청인지·같은 방/사용자인지 확인하지 않는다.
- **실제 재현 결과:** 순서 `A 대기 → B 성공 → A 거부 → A′ 성공`에서 서버 대역은 `state: idle`, `startedAt: null`이 됐다. 로컬 `lastPresenceSig`는 B의 studying 값을 그대로 갖는다. 같은 B를 다시 호출해도 쓰기가 추가되지 않았다. 변경 전 `9da349d`의 실제 `syncPresence`로 같은 순서를 돌리면 새 studying 상태가 남아 이번 재전송 추가로 생긴 회귀임을 확인했다.
- **영향:** 사용자는 공부 중인데 다른 사람에게 쉬는 중으로 보인다. 원본 공부 세션을 삭제하는 문제는 아니지만, 라운지의 핵심 현재 상태가 틀린다. 포그라운드 하트비트(`studyRoom.js:554`)는 `updatedAt`만 고쳐서 복구하지 못한다. 헤드리스도 `startedAt`을 되살리지 않으므로 완전한 복구가 아니다. 다음 상태 변화나 강제 전체 동기화가 있어야 회복될 수 있다.
- **고칠 방향:** 방·UID·요청 세대별로 최신 전송을 관리하고, 축소 재시도와 성공/실패 후 캐시 변경 모두 최신 요청일 때만 허용한다. 오래된 실패가 새로운 상태를 덮거나 새로운 성공의 캐시를 지우지 못하게 한다. 동일한 지연 거부→재개 순서를 회귀 검사에 넣는다. 실제 운영에서 이 순서가 얼마나 자주 생기는지는 별도 확인 대상이다.

### P2 — 고쳐야 할 문제

#### W-02. 라운지를 열거나 앱에 복귀하면 정상 온기를 삭제한다

- **재현 조건:** 공부를 멈춰 `endedAt`이 저장된 뒤, 후속 타이머/세션 변화가 없는 상태에서 라운지를 연다. 또는 잠시 다른 앱에 갔다 돌아온다.
- **근거:** `src/screens/StudyRoomScreen.js:178`~`:181`와 `src/hooks/useAppState.js:978`~`:985`는 새 `sendStudyPresence`를 거치지 않고 `buildPresence`/`buildStudyPresence`를 직접 부르며 `endedAt`을 전달하지 않는다. `src/utils/studyRoomCore.js:140`은 이 경우 `endedAt: null`을 반환한다. `update`에서 null은 생략이 아니라 삭제다.
- **재현 결과:** 종료 1분 뒤 `warm=0.9667`인 상태에 진입 경로의 payload를 적용하면 `endedAt`이 사라지고 `warm=0`이 됐다. 메인 effect가 다시 실행될 조건이 없으면 그대로다. 앱 복귀 경로는 시그니처까지 강제로 비우므로 이 삭제를 막지도 않는다.
- **고칠 방향:** 종료·진입·복귀·재입장이 같은 끝 시각 정책을 사용하는 전송 경로를 공유하게 한다. ‘끝 시각을 모르는 idle 재전송’과 ‘새 공부를 시작해 이전 끝 시각을 지우는 전송’을 구별한다. 메인 effect 한 곳에만 새 필드를 넣는 것으로는 충분하지 않다.

#### W-03. 백그라운드에서 오래전에 끝난 공부가 복귀 순간 막 끝난 것으로 되살아난다

- **재현 조건:** 프로세스가 살아 있는 채 카운트다운을 돌려 `presenceWasRunningRef=true`가 된 후, JS가 멈춘 백그라운드에서 타이머가 끝난다. 종료 30분 이상 뒤 복귀하여 캐치업이 타이머를 완료 상태로 만든다.
- **근거:** 백그라운드 완료 처리는 `src/hooks/useAppState.js:941` 이후이고, `:2467`은 이전에 running이었고 지금 active가 없다는 이유만으로 **현재 `Date.now()`**를 저장한다. 실제 종료 시각이나 복귀 캐치업 여부를 보지 않는다.
- **재현 결과:** 실제 끝은 100분 전인 완료 세션을 넣고 실제 `sendStudyPresence` 콜백을 실행했는데, 새 payload의 끝 시각은 현재였고 `warm=1`이었다. 이미 식은 자리가 다시 30분간 따뜻해진다. 기능을 꺼 둔 동안 종료됐다가 다시 켜는 등 전환을 뒤늦게 관측하는 경우도 같은 원리를 점검해야 한다.
- **고칠 방향:** 직접 종료/일시정지 이벤트와 자동 완료·복원 캐치업을 구분한다. 자동 완료에는 해당 타이머의 벽시계 종료 근거를 쓰고, 끝을 모르면 현재 시각으로 꾸미지 않는다. presence를 보내는 시각과 공부가 끝난 시각을 분리한다.

#### W-04. 재시작 복원용 세션 endedAt은 실제 멈춘 시각이 아니다

- **재현 조건 1:** 오늘 첫 공부를 일시정지하고 앱을 종료·재시작한다. 완료 세션이 없으면 새 ref는 false/null이고, 복원된 paused 타이머는 active가 아니므로 끝 시각을 복구하지 못한다. 서버에 남았던 온기도 null 전송으로 지울 수 있다.
- **재현 조건 2:** 공부 중 긴 일시정지가 있었다가 완료하고 재시작한다. `buildSessionRecord`의 끝 시각은 `startedAt + durationSec`이므로 쉬었던 시간만큼 과거다. 60분 쉬고 10분 공부한 예에서는 방금 끝냈어도 대체값이 60분 전이라 `warm=0`이었다. ‘조금 이른 정도’로 제한되는 차이가 아니다.
- **재현 조건 3:** 전날 23시대에 시작해 오늘 00:05에 끝낸 세션 후 재시작한다. 세션 `date`는 시작일이라 `lastEndedAtToday`가 오늘의 최근 종료를 제외한다.
- **근거:** `src/utils/studyRoomCore.js:148`~`:155`, `src/hooks/useAppState.js:2461`~`:2473`, `src/utils/timerCore.js:140`~`:160`의 세션 시각·시작일 귀속 계약.
- **고칠 방향:** 기존 세션 endedAt/날짜의 의미를 바꾸지 말고, 실제 종료·일시정지 시각을 presence용으로 별도 보존한다. 재시작 때도 그 근거를 복원하고 방/계정 변경 시 수명을 정한다. 온기의 30분 판정은 실제 경과시간 기준으로 하며, ‘시작일이 오늘인가’로 최근 종료를 자르지 않는다. 실측 종료가 없는 옛 기록은 정확한 시각처럼 단정하지 않는다.

#### W-05. 축소 전송 성공을 전체 payload 성공으로 기억해 endedAt의 복구를 막는다

- **재현 조건:** 첫 전송이 실패해 endedAt 없는 재전송만 성공한다. 이후 같은 idle/같은 endedAt을 다시 보내거나 규칙이 정상으로 복구돼도 같은 시그니처다.
- **근거:** `src/utils/studyRoom.js:522`~`:536`. 캐시는 endedAt을 포함한 원래 시그니처인데, `rest`가 성공하면 곧바로 return한다. 실패 종류도 구별하지 않아 endedAt 미지원이 아닌 오류까지 필드 제거로 처리한다.
- **재현 결과:** 첫 요청 실패→축소 성공 뒤 같은 payload를 한 번 더 호출해도 총 쓰기 시도는 2회 그대로였다. 서버 대역에는 endedAt이 없고 로컬 캐시에만 있다. 기존 값이 있었다면 필드 생략으로 그 과거 값이 남을 수도 있다.

#### W-07. 새 책 그림도 라이트 유색 좌석에서 대비 여유가 부족하다

- **재현 조건:** `ae3c296`의 새 책을 라이트 네이비 idle 좌석에서 3권으로 본다. 온기가 남아 있을 때는 좌석 책 대신 ‘방금 전까지’를 보여주므로 온기 만료 후도 확인한다.
- **근거:** `src/screens/StudyRoomScreen.js:42`~`:67`의 표지/종이 색과 `:575`의 idle `T.surface2`. 배경값은 `src/constants/colors.js:76` 이후다.
- **수치 확인:** 세 번째 표지 `#6B9A5B` 대 배경 `#C0D0E8`는 **2.099:1**, 종이 `#FBF3E2` 대 그 배경은 **1.416:1**이다. 공부량 구간을 읽는 그림이므로 [W3C의 의미 있는 비문자 그래픽 대비 3:1 설명](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)을 설계 기준으로 삼으면 외곽 대비 여유가 작다. 네이티브 앱 전체의 WCAG 적합성 판정이나 실제 읽기 실패를 확정한 것은 아니다.
- **고칠 방향:** 유색 좌석에서도 형태를 읽을 수 있는 표지 색이나 외곽선을 검토하고, 원래 크기에서 2권과 3권 구분을 확인한다. 흰 명단 카드 위 세 번째 표지는 약 3.282:1이므로 좌석과 명단을 같은 배경으로 계산하면 안 된다.
- **후속 커밋 반영:** 최초 단색 막대는 12×2.5dp였지만 새 기본 책은 16×4.5dp이고 종이·책등 띠가 생겼다. 따라서 옛 색 수치로 새 그림을 평가하지 않았다. 다크 모드는 밝은 종이가 구분 단서가 되므로 낮은 표지 대비만으로 새 책 전체가 안 보인다고 판정하지 않는다. 그 점과 실제 기기 미확인을 반영해 P3로 둔다.

큰 글꼴에서의 실제 잘림·줄바꿈은 아래 기기 확인 항목으로 남긴다. 코드만 보고 실제 화면이 깨진다고 확정하지 않았다.

### OTA와 규칙 호환

**이번 두 커밋만으로 새 네이티브 바이너리가 필요해지는 의존성은 발견하지 못했다.** 변경은 JS·기존 RN View/Text·기존 Firebase JS SDK와 RTDB 필드/규칙이다. 패키지·네이티브 모듈·플러그인·네이티브 설정 추가가 없다. `app.config.js:11`의 버전은 `1.0.43`, `:17`은 `runtimeVersion: { policy: 'appVersion' }`다. 따라서 기존 1.0.43 네이티브 기능 범위 안의 JS 변경으로 판단한다. Expo도 [네이티브 코드와 업데이트가 호환돼야 하며 appVersion 정책은 앱 버전으로 runtime을 구분한다](https://docs.expo.dev/eas-update/runtime-versions/)고 설명한다.

이것은 **이 변경의 네이티브 의존성 검토**다. 실제 배포 대상 바이너리·채널·업데이트 번들의 일치나 별도 미커밋 Live Activity 변경까지 승인한 것은 아니다. P1/P2와 기기 확인을 남긴 채 runtime 문자열이 같다는 이유로 내보내면 안 된다.

저장소 규칙의 endedAt은 선택적 숫자이며, running의 null 삭제도 가능한 구조다. 운영에만 있던 `cheers.nick`을 보존한 것은 옛 writer 호환을 고려한 조치다. 현재 표시 코드는 nick을 사용하지 않는다. **운영 규칙 게시·게시 후 일치는 요청서의 확인 기록을 인용한 것이고, 이번 검토에서 콘솔을 재조회하거나 게시하지 않았다.**

**처리방침에는 ‘마지막으로 공부를 멈춘 시각(종료·일시정지)’을 추가하는 것이 맞다.** 저장소 `privacy-policy.html:37`의 공유 정보에는 아직 이 항목이 없다. 표시가 30분 후 사라져도 RTDB의 필드가 그때 자동 삭제되는 것은 아니므로 ‘30분 보관 후 삭제’라고 쓰면 안 된다. 다음 공부 시작의 null 갱신·새 종료의 덮어쓰기·방 탈퇴/기능 해제 같은 실제 정리 경로와 맞춰 설명해야 한다. 요청대로 문구는 수정하지 않았다.
